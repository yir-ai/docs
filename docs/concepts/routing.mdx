A model on Yir can be served by several **provider channels**: the model maker's official API and other certified suppliers. For each Job, Yir picks an eligible channel, and if an attempt is confirmed failed, it can fall back to another channel, staying within your `max_cost` when you set one.

You influence this with the optional `routing` object on quote and generation requests. Without it, the Routing Profile bound to your API Key applies (see [Console routing](/docs/console#routing-profiles)).

```json
{
  "routing": {
    "preference": "cost",
    "only": ["official", "fal"],
    "variants": { "fal": "standard" },
    "fallback": true
  }
}
```

## Fields

| Field | Values | Effect |
| --- | --- | --- |
| `preference` | `cost`, `speed` | `cost` orders channels by estimated price, lowest first. `speed` orders channels by their observed upstream generation time (median over recent Jobs); channels with too few recent Jobs come after, ordered by price. Defaults to the key's Routing Profile (`cost` unless you change it). `balanced` is a deprecated alias of `cost` and is still accepted. |
| `only` | 1–16 channel IDs | Unordered allowlist. Selection and fallback stay inside it. A single entry pins one channel, which is useful for testing. |
| `variants` | Map of channel ID → variant | Chooses a specific version of a channel. See below. |
| `fallback` | `true`, `false` | `false` allows only one provider attempt, except after an unbilled content rejection (see [below](#content-rejections)). Defaults to the key's Routing Profile. |
| `fidelity` | `original`, `genuine`, `any` | Minimum faithfulness of the channel's output to the model's native output. See [Fidelity](#fidelity). Defaults to the key's Routing Profile. |
| `accelerate` | `true`, `false` | Starts the next route when an image attempt runs well past its usual time with no result. See [Acceleration](#acceleration). Defaults to the key's Routing Profile. |

Custom ordering (`order`) is not supported. Invalid routing values fail with `400 YIR_INVALID_ROUTING_OVERRIDE`.

**Tip: don't use `only` to control cost.** Channels outside `only` never take part in fallback, so when every listed channel fails or is unavailable, the Job fails even if another channel could finish it. To cap what a Job can cost, set `max_cost` and leave room for a fallback channel (see [quotes and billing](/docs/concepts/billing)). To avoid channels that alter the output, use `fidelity`. Use `only` for targeted tests, or when your use case requires specific channels.

## How speed-first routing selects a channel

`routing.preference: "speed"` selects among eligible channels for **the same model and the current request specification**. It does not switch models or guarantee the fastest channel for every request.

Selection follows this order:

1. **Filter for executable routes.** The key's Routing Profile, `only`, `variants`, `fidelity`, model parameters and channel availability still apply, as does `max_cost` when set. Speed-first routing does not bypass these restrictions.
2. **Prefer healthy channels and the requested quality tier.** Degraded channels follow healthy ones. A route that serves the request by upgrading to a higher quality tier, at a higher price than a route serving the requested tier, follows those requested-tier routes as a fallback.
3. **Compare historical median upstream duration (P50).** Among candidates otherwise equal on the preceding conditions, routes with valid speed statistics lead, with lower P50 first. Statistics are separate for each channel route (including its variant) and exact request specification. Timing for a different resolution, aspect ratio or quality tier is not directly substituted for your request.
4. **Use price for the remaining order.** Equal P50 values, or candidates without valid speed statistics, are ordered by price, lowest first. Routes without valid speed statistics follow routes with valid statistics.

A P50 of 30 seconds means roughly half of the valid historical samples completed upstream within 30 seconds. **It is not a deadline for your request.** Speed statistics must meet validity requirements; currently at least 5 valid duration samples are required, and expired statistics are not used. Current upstream queues can still differ from historical conditions.

This compares **upstream execution time**. Your end-to-end wait also includes input preparation, scheduling and result delivery, so P50 is not the full time from submitting a request to downloading its result.

### Why can speed-first routing still select a discounted variant?

A discount describes price, not necessarily slower execution. A discounted variant may have a lower valid P50, or it may win on price when candidates lack valid speed statistics or have equal P50 values. A more expensive standard variant is not guaranteed to finish faster every time.

`speed` controls selection order; `fallback` controls switching after eligible failures (with the [content-rejection exception](#content-rejections)); `accelerate` controls starting the next route when an image attempt remains unresolved for too long. **Speed-first routing does not race multiple channels in parallel**, or treat an ordinary delay as a failure. See [Acceleration](#acceleration) for its triggers and billing.

## Custom channel examples

These are `routing` fragments to merge into a quote or generation request. You still need the model, inputs and other fields required by that endpoint. Check [Model Market](https://yir.ai/models) for channels and variants supporting your model and specification, then quote with the same parameters. Changing channels or variants can change the price.

### Prefer speed across all eligible channels

```json
{
  "routing": {
    "preference": "speed",
    "fallback": true,
    "accelerate": true
  }
}
```

Omitting `only` keeps all eligible channels permitted by the key's policy. Acceleration applies only to images and still requires an eligible next route.

### Use only APIMart's standard variant, while keeping other channels

For example, for a GPT Image 2.5 model that supports APIMart's standard variant:

```json
{
  "routing": {
    "preference": "speed",
    "variants": { "apimart": "standard" },
    "fallback": true
  }
}
```

This excludes APIMart's `ext` variant. It **does not force APIMart to run first** or exclude other channels, which still participate in speed ranking and fallback. To use only APIMart's standard variant, also add `"only": ["apimart"]`; doing so removes cross-channel fallback.

### Prefer speed within a chosen set of channels

```json
{
  "routing": {
    "only": ["apimart", "kie"],
    "variants": { "apimart": "standard" },
    "preference": "speed",
    "fallback": true
  }
}
```

Selection and fallback stay within eligible APIMart standard and KIE routes. `only` is an unordered allowlist: appearing first does not give a channel priority, and `fallback: true` does not permit channels outside the list. If neither is available, Yir does not automatically use the official channel or another provider.

For persistent rules on a key, configure speed preference and channel exclusions in [Console Routing Profiles](/docs/console#routing-profiles), and check that the key is bound to that profile. You can exclude a whole channel, a special-price tier, or a channel for a specific model. Request-level settings cannot re-enable channels excluded by the key's policy. Narrowing the eligible set leaves fewer options for speed and fallback.

## Channel IDs and the official alias

Channel IDs are lowercase identifiers such as `openai`, `google`, `fal`, or `kie`. Model detail pages in [Model Market](https://yir.ai/models) list the channels and variants that serve each model.

`official` is an alias for the current model maker's own channel. Yir resolves it before validation, so `only: ["official"]` on an OpenAI model is the same as `only: ["openai"]`. Responses always report the real channel ID, for example in `final_provider`.

## Channel variants

Some channels offer more than one version of a model, for example a standard and a faster or cheaper variant, each with its own upstream model, price, and capabilities. The public parameters of the model stay the same.

- **No entry for a channel:** all of its eligible variants may be used.
- **`"standard"`:** only the channel's standard version.
- **Another variant name:** only that variant. If it is unknown or unavailable, Yir does not substitute another variant of the same channel; other allowed channels still follow the fallback rules.

When `only` is present, every channel in `variants` must also be in `only`.

### Variants can serve different requests

Variants of the same channel can differ in billing and in the specifications they serve. For example, APIMart's GPT Image 2.5 standard version is billed by tokens and serves every quality tier, while its `ext` version charges a fixed price per image, offers fewer aspect ratios, and serves only `low` and `medium`.

- A variant that does not support a request's parameters is excluded from routing and fallback for that request. If `only` and `variants` leave no variant that supports it, the quote reports `no_matching_supply` and the request is rejected.
- [Model Market](https://yir.ai/models) compares prices per exact specification: a variant is listed only under the specifications it supports, and it is marked when it does not serve the selected quality tier.

## Fidelity

Some channels return output that is not the model's native result, for example a 1K image upscaled to 4K, or an image made in the vendor's consumer app instead of its API. Yir grades each channel route and tier from C2PA Content Credentials and its own tests, and `fidelity` sets the lowest grade a request accepts:

| Value | Channels used |
| --- | --- |
| `genuine` | Default. Skips routes known to upscale or otherwise alter output. |
| `original` | Only routes tested as the vendor's original API output, and the vendor's official channel. |
| `any` | No filter. Upscaling channels are often cheaper. |

The default comes from `default_fidelity` on the Routing Profile bound to your API Key (`genuine` unless you change it in [Console](/docs/console#routing-profiles)); `routing.fidelity` on a request overrides it. The filter applies after `only` and channel exclusions and before pricing, so a stricter value can raise the price. It is fixed when the Job is admitted.

If no channel meets the floor, generation fails with `422 YIR_FIDELITY_EXCLUDED`, and a quote returns `supply.available: false` with `issues: ["no_matching_supply"]`. Relax `fidelity`, or choose another model or specification.

Each delivered file reports what was actually checked, in `result.files[].fidelity`:

```json
{ "url": "https://...", "media_type": "image/png", "fidelity": { "grade": "original", "reason": "vendor_signed" } }
```

| `grade` | Meaning |
| --- | --- |
| `original` | Vendor's API output: valid vendor signature, content unchanged. |
| `app` | Vendor's consumer app output (for example ChatGPT): valid vendor signature, content unchanged. |
| `equivalent` | No valid vendor signature, but evidence that the output was not upscaled or changed. |
| `altered` | Upscaled, changed after signing, or below the requested size or duration. |
| `unverified` | No evidence either way. |

`reason` is a short machine-readable code explaining the grade. Results delivered before grading existed have no `fidelity`. Fidelity filters on each route's tested grade, so it lowers the chance of an upscaled result but is not a guarantee; check `grade` on files you present as the model's own output.

## How fallback works

Yir moves to another channel after the current attempt is **confirmed failed**. With [acceleration](#acceleration), it also starts the next route when an image attempt runs well past its usual time. Otherwise Yir does not abandon an attempt for being slow or unknown. By default a Job may try up to three channels, at most two third-party and one official, in `preference` order (the official channel can come first), subject to:

- your `only` and `variants` choices, and any restriction on the key's Routing Profile;
- the model and parameters each channel supports;
- current channel availability;
- your `max_cost`, when set: channels whose estimate exceeds what remains of it after earlier attempts' charges are skipped.

Channels skipped before submission do not count as attempts. An official reference price in a quote does not guarantee that the official channel will run.

### Content rejections

Channels moderate content differently, so a prompt one channel rejects may pass on another. When a channel rejects the prompt or references for content safety **and does not bill the attempt**, Yir tries up to two more channels, even with `fallback: false`. These attempts stay inside `only`, `variants`, the key's Routing Profile and `max_cost`, do not count toward the three-attempt limit, and never retry the channel that rejected. An unbilled rejection costs nothing. If no channel accepts it, or none remains, the Job fails with `YIR_CONTENT_REJECTED`. A rejection the channel billed or may have billed (for example output it generated and then blocked), or one from Yir's own check of reference images, ends the Job without switching.

**Warning: a tight `max_cost` can interrupt delivery during failover.** Even after a Job is accepted, a failed channel may need to be replaced by a more expensive one. If its estimate exceeds the remaining budget after earlier billed attempts, Yir skips it; if no eligible fallback fits, the Job fails with `YIR_BUDGET_EXCEEDED` and may deliver no result. When delivery continuity is more important than a per-Job spending cap, omit this optional field; otherwise leave room for more expensive fallback channels and earlier attempts' charges. Omitting it removes the per-Job cap, so actual charges can exceed the quote; account balance and other limits still apply.

## Acceleration

Upstream channels occasionally leave a task unresolved for far longer than usual. With `accelerate` on, when an image attempt reaches its cutoff with no result, Yir starts the next route. The cutoff comes from recent timing for that channel and specification, usually 1.5 to 13 minutes, and can be shorter while a channel is slow.

- **It needs a next route.** Acceleration follows the fallback rules above: `fallback` on, within `only` and `variants`, within what remains of `max_cost` and your balance, and under the three-attempt limit. If no next route remains, Yir keeps waiting for the current attempt.
- **Once per Job.** A Job is accelerated at most once, and only image attempts with a low estimated price qualify.
- **The first result is delivered.** The cut-off attempt is not cancelled and can run alongside the next route. Whichever finishes first supplies the result, and a Job delivers only one. If the next route fails, the cut-off attempt can still supply the result.
- **Billing.** If upstream bills both attempts, both actual costs are charged and count toward `max_cost`.
- **Images only.** Video Jobs are never accelerated: video attempts are expensive, and a cut-off attempt can still be billed.

The default comes from `default_accelerate` on the Routing Profile bound to your API Key (on unless you change it in [Console](/docs/console#routing-profiles)); `routing.accelerate` on a request overrides it. Set it to `false` to avoid switching channels over long waits, for example when you would rather wait on a slow, cheaper channel than risk paying for a second attempt. In Console Logs, a cut-off attempt is shown as **Accelerated to another channel**.

## Parameters that differ by channel

A few parameters are handled differently by different channels. When a channel ignores one of your parameters, Yir reports it:

- Quotes include `parameter_notices` for the first channel and `parameter_handling_may_vary: true` if fallback channels may behave differently.
- Successful Jobs and their Webhooks include the `parameter_notices` of the attempt that produced the result.
- When a channel returns more than you asked for and the result is still usable, Yir delivers it instead of failing the Job, adds a notice with `disposition: "exceeded"`, and charges no more than the quote:
  - More outputs than `n`: only the last `n` are delivered (`output_count_exceeded`).
  - A higher resolution with the requested aspect ratio: delivered (`resolution_exceeded`).
  - A video with audio when you sent `generate_audio: false`: delivered (`audio_included`).
  - A 3D model with a texture or PBR maps when you sent `texture: "none"` or `pbr: false`: delivered (`texture_included`, `pbr_included`).
- Fewer outputs, a different aspect ratio or duration, a lower resolution, or missing audio when you asked for it still fail.

Some parameters instead limit which channels can run. For GPT Image, `quality` is a minimum tier: only channels that serve the requested tier take part in routing and fallback, and the parameter is never ignored. Each model page lists the channels and the tiers they serve, for example [GPT Image 2](/docs/models/openai/gpt-image-2#quality) and [GPT Image 2.5](/docs/models/openai/gpt-image-2-5-flare#quality).

Routing cannot bypass authentication, balance, spend limits, specification checks, or Yir's attempt limits, and it cannot select credentials.
