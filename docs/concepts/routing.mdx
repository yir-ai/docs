---
title: Routing and fallback
description: Control which provider channels and channel variants may run a request, and how fallback works.
---

A model on Yir can be served by several **provider channels**: the model maker's official API and other certified suppliers. For each Job, Yir picks an eligible channel, and if an attempt is confirmed failed, it can fall back to another channel, staying within your `max_cost` when you set one.

You influence this with the optional `routing` object on quote and generation requests. Without it, the Routing Profile bound to your API Key applies (see [Console routing](/docs/console#routing-profiles)).

```json
{
  "routing": {
    "preference": "cost",
    "only": ["official", "fal"],
    "variants": { "fal": "standard" },
    "fallback": true
  }
}
```

## Fields

| Field | Values | Effect |
| --- | --- | --- |
| `preference` | `cost`, `speed` | `cost` (default) orders channels by estimated price, lowest first. `speed` orders channels by their observed upstream generation time (median over recent Jobs); channels with too few recent Jobs come after, ordered by price. `balanced` is still accepted as a deprecated alias of `cost`. Defaults to the key's Routing Profile. |
| `only` | 1–16 channel IDs | Unordered allowlist. Selection and fallback stay inside it. A single entry pins one channel, which is useful for testing. |
| `variants` | Map of channel ID → variant | Chooses a specific version of a channel. See below. |
| `fallback` | `true`, `false` | `false` allows only one provider attempt. Defaults to the key's Routing Profile. |
| `fidelity` | `original`, `genuine`, `any` | Minimum faithfulness of the channel's output to the model's native output. See [Fidelity](#fidelity). Defaults to the key's Routing Profile. |
| `accelerate` | `true`, `false` | Moves an image attempt that stalls far past its channel's usual completion time to the next route. See [Acceleration](#acceleration). Defaults to the key's Routing Profile. |

Custom ordering (`order`) is not supported. Invalid routing values fail with `400 YIR_INVALID_ROUTING_OVERRIDE`.

## Channel IDs and the official alias

Channel IDs are lowercase identifiers such as `openai`, `google`, `fal`, or `kie`. Model detail pages in [Model Market](https://yir.ai/models) list the channels and variants that serve each model.

`official` is an alias for the current model maker's own channel. Yir resolves it before validation, so `only: ["official"]` on an OpenAI model is the same as `only: ["openai"]`. Responses always report the real channel ID, for example in `final_provider`.

## Channel variants

Some channels offer more than one version of a model, for example a standard and a faster or cheaper variant, each with its own upstream model, price, and capabilities. The public parameters of the model stay the same.

- **No entry for a channel:** all of its eligible variants may be used.
- **`"standard"`:** only the channel's standard version.
- **Another variant name:** only that variant. If it is unknown or unavailable, Yir does not substitute another variant of the same channel; other allowed channels still follow the fallback rules.

When `only` is present, every channel in `variants` must also be in `only`.

### Variants can serve different requests

Variants of the same channel can differ in billing and in the specifications they serve. For example, APIMart's GPT Image 2.5 standard version is billed by tokens and serves every quality tier, while its `ext` version charges a fixed price per image, offers fewer aspect ratios, and serves only `low` and `medium`.

- A variant that does not support a request's parameters is excluded from routing and fallback for that request. If `only` and `variants` leave no variant that supports it, the quote reports `no_matching_supply` and the request is rejected.
- [Model Market](https://yir.ai/models) compares prices per exact specification: a variant is listed only under the specifications it supports, and it is marked when it does not serve the selected quality tier.

## Fidelity

Some channels return output that is not the model's native result, for example a 1K image upscaled to 4K, or an image made in the vendor's consumer app instead of its API. Yir grades each channel route and tier from C2PA Content Credentials and its own tests, and `fidelity` sets the lowest grade a request accepts:

| Value | Channels used |
| --- | --- |
| `genuine` | Default. Skips routes known to upscale or otherwise alter output. |
| `original` | Only routes tested as the vendor's original API output, and the vendor's official channel. |
| `any` | No filter. Upscaling channels are often cheaper. |

The default comes from `default_fidelity` on the Routing Profile bound to your API Key (`genuine` unless you change it in [Console](/docs/console#routing-profiles)); `routing.fidelity` on a request overrides it. The filter applies after `only` and channel exclusions and before pricing, so a stricter value can raise the price. It is fixed when the Job is admitted.

If no channel meets the floor, generation fails with `422 YIR_FIDELITY_EXCLUDED`, and a quote returns `supply.available: false` with `issues: ["no_matching_supply"]`. Use `genuine` or `any`, or choose another model or specification.

Each delivered file reports what was actually checked, in `result.files[].fidelity`:

```json
{ "url": "https://...", "media_type": "image/png", "fidelity": { "grade": "original", "reason": "vendor_signed" } }
```

| `grade` | Meaning |
| --- | --- |
| `original` | Vendor's API output: valid vendor signature, content unchanged. |
| `app` | Vendor's consumer app output (for example ChatGPT): valid vendor signature, content unchanged. |
| `equivalent` | No valid vendor signature, but evidence that the output was not upscaled or changed. |
| `altered` | Upscaled, changed after signing, or below the requested size or duration. |
| `unverified` | No evidence either way. |

`reason` is a short machine-readable code explaining the grade. Results delivered before grading existed have no `fidelity`. Fidelity filters on each route's tested grade, so it lowers the chance of an upscaled result but is not a guarantee; check `grade` on files you present as the model's own output.

## How fallback works

Yir moves to another channel after the current attempt is **confirmed failed**, or, with [acceleration](#acceleration), when an image attempt stalls far past its channel's usual completion time. Otherwise slow or unknown attempts are not abandoned. By default a Job may try up to three channels, at most two third-party and one official, in `preference` order (the official channel can come first), subject to:

- your `only` and `variants` choices, and any restriction on the key's Routing Profile;
- the model and parameters each channel supports;
- current channel availability;
- your `max_cost`, when set: channels whose estimate exceeds what remains of it after earlier attempts' charges are skipped.

Channels skipped before submission do not count as attempts. An official reference price in a quote does not guarantee that the official channel will run.

## Acceleration

Upstream channels occasionally leave a task unresolved for far longer than usual. With `accelerate` on, when an image attempt is still unresolved upstream at about twice that channel's recent p99 completion time (at least 5 minutes; roughly 10 to 15 minutes on today's image channels), Yir cuts it off and retries on the next route.

- **It needs a next route.** Acceleration follows the fallback rules above: `fallback` on, within `only` and `variants`, within what remains of `max_cost` and your balance, and under the three-attempt limit. If no next route remains, Yir keeps waiting for the current attempt.
- **One attempt at a time.** Yir does not race channels in parallel. The cut-off attempt never supplies the result, even if it finishes later.
- **Billing.** If the cut-off attempt's upstream bills it anyway, that actual cost is charged like any other upstream-billed attempt and counts toward `max_cost`.
- **Images only.** Video Jobs are never accelerated: video attempts are expensive, and a cut-off attempt can still be billed.

The default comes from `default_accelerate` on the Routing Profile bound to your API Key (on unless you change it in [Console](/docs/console#routing-profiles)); `routing.accelerate` on a request overrides it. Set `{"accelerate": false}` to always wait for the first channel, for example when you would rather wait on a slow, cheaper channel than risk paying for a second attempt. In Console Logs, a cut-off attempt is shown as **Accelerated to another channel**.

## Parameters that differ by channel

A few parameters are handled differently by different channels. When a channel ignores one of your parameters, Yir reports it instead of hiding it:

- Quotes include `parameter_notices` for the first channel and `parameter_handling_may_vary: true` if fallback channels may behave differently.
- Successful Jobs and their Webhooks include the `parameter_notices` of the attempt that produced the result.

Some parameters instead limit which channels can run. For GPT Image, `quality` is a minimum tier: only channels that serve the requested tier take part in routing and fallback, and the parameter is never ignored. Each model page lists the channels and the tiers they serve, for example [GPT Image 2](/docs/models/openai/gpt-image-2#quality) and [GPT Image 2.5](/docs/models/openai/gpt-image-2-5-flare#quality).

Routing cannot bypass authentication, balance, spend limits, specification checks, or Yir's attempt limits, and it cannot select credentials.
