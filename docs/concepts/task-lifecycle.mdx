---
title: Job lifecycle
description: Job states, polling, cancellation, unknown outcomes, and how long results are kept.
---

Every generation request creates one **Job**. The Job keeps the same ID from submission to its final result, even when Yir tries more than one provider channel behind the scenes.

## States

| Status | Meaning | Terminal |
| --- | --- | --- |
| `queued` | Accepted and waiting to start. | No |
| `running` | A provider attempt is in progress. Fallback attempts also happen in this state. | No |
| `delivering` | The provider returned a result; Yir is copying it to its own storage. | No |
| `succeeded` | The result is delivered and available under `result`. | Yes |
| `failed` | No attempt produced a deliverable result. See `error.code`. | Yes |
| `cancelled` | Cancelled before any provider submission started. | Yes |

```mermaid
stateDiagram-v2
  [*] --> queued
  queued --> running
  queued --> cancelled
  queued --> failed
  running --> delivering
  running --> failed
  delivering --> succeeded
  delivering --> failed
```

These six states are the whole public contract. Provider-specific states and internal orchestration steps are never exposed.

## Polling

Use two endpoints:

- `GET /v1/jobs/{id}/status` returns a small summary (`id`, `status`, `error`, optional `cancellation`). Use it for repeated polling.
- `GET /v1/jobs/{id}` returns the complete Job, including `result`, `billing`, `usage`, and `parameter_notices`. Read it once the status is terminal.

Recommended pacing, also used by the SDKs: every 5 seconds for the first 30 seconds, every 10 seconds until about 90 seconds, then every 20 seconds. Always set an overall deadline in your application.

:::warning
A slow Job, a request timeout, or a provider that has not answered yet is **not** a failure. Keep querying the same Job ID. Do not submit a replacement request.
:::

Stopping your local polling (a timeout, an `AbortSignal`, a cancelled context, a closed browser tab) only stops waiting. It does not cancel the Job, and it does not mean the Job failed. Save the Job ID and resume later.

To avoid polling entirely, set `webhook_url` and receive the terminal Job by [Webhook](/docs/guides/webhooks).

## Cancellation

Request cancellation with `POST /v1/jobs/{id}/cancel`. The effect depends on how far the Job has progressed:

- **Before any provider submission**, the Job becomes `cancelled` immediately and its reserved funds are released.
- **After a provider submission**, the response carries `cancellation.status: "stop_requested"`. Yir starts no further fallback attempts, but the current attempt keeps running. If it succeeds, the result is delivered and charged; if it fails, the Job ends as `failed` with no charge.

Show "Stop requested" in your UI in the second case and keep polling. Cancelling a Job that is already `succeeded` or `failed` returns `409 YIR_JOB_NOT_CANCELLABLE`. Repeating a cancel request is safe.

## Unknown outcomes

Occasionally a provider does not confirm whether an attempt succeeded. Yir keeps the Job active while it reconciles. If the outcome stays unknown for too long, Yir closes the Job as `failed` with `YIR_OUTCOME_TIMEOUT` and charges nothing. A result that arrives later does not reopen or charge the Job.

## Results and retention

| What | Available until |
| --- | --- |
| Result files | 7 days after the Job was created (can be earlier for some results) |
| Individual result URL | `result.files[].expires_at`, often sooner than the file itself |
| Job record and summary log | 90 days after creation; afterwards queries return `404` |

While a result is kept, `result.availability` is `available` and `result.files` lists signed download URLs. If a URL has expired, query the Job again for a fresh one. When the retention window ends, the Job stays `succeeded` but `result.availability` becomes `expired` and no files are returned.

Yir is not an asset library. Copy every result you need to your own storage as soon as the Job succeeds.

A successful Job can carry `result.warnings: ["additional_results_unavailable"]` when an optional extra output (for example a video's last frame) could not be delivered. The Job is still successful and is charged normally.

## Applying terminal results once

The same terminal Job can reach you twice: once from polling and once from a Webhook, or from a Webhook redelivery. Make your business actions (saving files, updating credits, marking orders complete) idempotent by Job ID so each Job is applied exactly once.
