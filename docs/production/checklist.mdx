## Checklist

- The API Key lives only on your server, with a separate key per environment.
- Every submission has a persisted idempotency key, reused for retries of the same request.
- The request, key, and Job ID are stored together before and after submission.
- Polling is bounded, backs off, and stops only locally.
- Terminal results are applied once per Job ID, whether they arrive by polling or Webhook.
- Webhook signatures are verified on raw bytes, and events are deduplicated.
- Result files are copied to your storage before they expire.
- Spending is controlled with an optional `max_cost`, balance alerts, and per-key monthly limits.
- Error handling branches on `error.code` and `error.action`.

## Idempotent submission

Every generation request must carry an `Idempotency-Key` header (1–200 characters). It turns a submission into a safe-to-retry operation:

- Same key and identical request: Yir returns the original Job instead of creating another.
- Same key and a different request: rejected with `409 YIR_IDEMPOTENCY_CONFLICT`.
- Missing or blank key: rejected with `400 YIR_INVALID_REQUEST` before any Job is created.

Generate one key per logical generation (for example `order-123-image-1`) and **store it with the request before you send it**. If the submission times out or your process crashes, send the same request with the same key again. Never create a fresh key because a response was slow; the first request may already have been accepted.

Keep the complete request unchanged, including `max_cost`, `routing`, references, and `webhook_url`. Do not re-quote and change `max_cost` under an existing key.

## Persist the right facts

Store these together for each generation:

| Field | Why |
| --- | --- |
| Your own request ID | Links the Job to your business object. |
| Request body and idempotency key | Lets you recover an unknown submission. |
| Yir Job ID | The only handle for status, results, and cancellation. |
| Last observed status | Lets you resume polling after a restart. |
| Whether the terminal result was applied | Prevents double-charging or double-crediting. |

Never store the API Key next to Job records.

## Waiting for results

Choose one or combine both:

- **Polling:** long-poll `GET /v1/jobs/{id}/status?wait=20` (or back off at 5 s, 10 s, then 20 s without `wait`), then read `GET /v1/jobs/{id}` once the status is terminal. See [long polling](/docs/concepts/task-lifecycle#long-polling).
- **Webhooks:** set `webhook_url` and handle the terminal Job. See [Webhooks](/docs/production/webhooks).

A common robust setup uses Webhooks as the primary signal and slow polling as a fallback for lost callbacks. Either way, apply the terminal Job **once per Job ID**.

## Recovery table

| Situation | What to do |
| --- | --- |
| Submission timed out or connection dropped | Resend the identical request with the same idempotency key. |
| Status query timed out | Retry the status query. The Job is unaffected. |
| Status is `queued`, `running`, or `delivering` | Wait and query again. Slow is not failed. |
| Local wait deadline reached | Stop waiting, keep the Job ID, resume later. Do not resubmit. |
| Status is `succeeded` | Read the full Job, copy `result.files`, record `billing.total_charged_by_yir`. |
| Status is `failed` | Read the full Job, handle `error.code`, and record `billing.total_charged_by_yir`: attempts the channel billed (such as billed output rejected as `YIR_CONTENT_REJECTED`) are charged at actual cost; most failures cost nothing. |
| Status is `cancelled` | Read the full Job. `error` may be `null`. Usually no charge, unless the channel billed an attempt before the stop; record `billing.total_charged_by_yir`. |
| Full Job query fails | Retry that query. Do not settle from the status summary alone. |
| `401`, `403`, or `404` | Fix the key, limit, or Job ID. Do not retry blindly. |
| `429 YIR_RATE_LIMITED` or `503` | Retry later with back-off; for `429`, wait at least `Retry-After` seconds. |

See [error codes](/docs/production/error-codes) for every code and its recommended action.

## Controlling cost

- Quote the request to see an estimate. The final charge follows the actual cost; set the optional `max_cost` when you need a hard cap per Job. See [quotes and billing](/docs/concepts/billing).
- Set a monthly spend limit on each API Key and a low-balance email alert in Console.
- Use `routing.fallback: false` if you prefer a single attempt over automatic recovery.

## Testing safely

Use a single-entry `routing.only` to test one channel, a separate API Key with a small monthly limit, and inexpensive parameters. Generation requests always create real Jobs and real charges.

## Support requests

Email [support@yir.ai](mailto:support@yir.ai) or use the support button in Console. Include the Job ID, endpoint, approximate UTC time, HTTP status, `error.code`, and the `request_id` from the error response. Never send your full API Key, prompts, source media, or signing secret.
