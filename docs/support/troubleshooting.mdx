---
title: Troubleshooting
description: Diagnose common authentication, submission, polling, result, and Webhook problems.
---

Look up specific codes in [error codes](/docs/support/error-codes). For the problems below, start with the first check listed.

<Accordion>
  <AccordionItem title="Every request returns 401">
    Confirm the header is exactly `Authorization: Bearer <key>` and that you are not sending `X-API-Key`. In Console, check whether the key was rotated, revoked, or has expired, and whether its IP allowlist includes your server's egress address. Never print the full key while debugging.
  </AccordionItem>
  <AccordionItem title="Submission returns 402 or 403">
    `402 YIR_INSUFFICIENT_BALANCE` means the balance does not cover the request's estimate or is negative; top up first. `403 YIR_SPEND_LIMIT_EXCEEDED` means this key reached its monthly limit; raise it in Console → API Keys.
  </AccordionItem>
  <AccordionItem title="Submission returns 422 YIR_NO_EXECUTABLE_ROUTE">
    No channel can run this exact request right now. Quote it and check `supply`. Remove a restrictive `routing.only` or `variants`, raise `max_cost`, or try other parameters.
  </AccordionItem>
  <AccordionItem title="The submit request timed out">
    Resend the identical request with the same idempotency key. You will get the original Job if it was accepted. A new key could create a second Job and a second charge.
  </AccordionItem>
  <AccordionItem title="409 YIR_IDEMPOTENCY_CONFLICT on a retry">
    The body changed between attempts. Retries must be byte-for-byte the same request: same parameters, references, `routing`, `max_cost`, and `webhook_url`. Load the saved request instead of rebuilding it.
  </AccordionItem>
  <AccordionItem title="The Job has been running for a long time">
    Keep querying the same Job ID. Slow or unconfirmed attempts are not failures, and a replacement request would run and charge separately. Videos can take several minutes. If the provider never confirms, Yir closes the Job as failed with `YIR_OUTCOME_TIMEOUT` and no charge.
  </AccordionItem>
  <AccordionItem title="I cancelled, but the Job still succeeded and was charged">
    After a provider submission, cancellation only stops further fallback attempts. The attempt already running can still succeed and is then charged. See [cancellation](/docs/concepts/task-lifecycle#cancellation).
  </AccordionItem>
  <AccordionItem title="The result URL returns 403 or has expired">
    Result URLs are short-lived. Query `GET /v1/jobs/{id}` for a fresh URL. If `result.availability` is `expired`, the 7-day retention has ended and the file is no longer available.
  </AccordionItem>
  <AccordionItem title="A parameter seems to have no effect">
    Check `parameter_notices` on the quote and the finished Job. Some channels ignore certain parameters; for example GPT Image ignores `quality` unless the request is pinned to the official channel.
  </AccordionItem>
  <AccordionItem title="Webhook signatures never verify">
    Verify the raw request bytes before any JSON parsing or re-serialization. Use the Webhook signing secret from Console → Webhooks, not your API key, and sign `timestamp + "." + id + "." + body`. Check that your server clock is accurate within 300 seconds.
  </AccordionItem>
  <AccordionItem title="The same Job was processed twice">
    Polling and Webhooks, or a Webhook and its retry, can report the same terminal Job. Deduplicate events by `Yir-Webhook-Id` and apply business effects once per `job.id`.
  </AccordionItem>
</Accordion>

## Contacting support

Include the Job ID, endpoint, approximate UTC time, HTTP status, `error.code`, and `request_id`. You may include the first few characters of the key. Never send the full API key, Webhook secret, prompts, or source media.
