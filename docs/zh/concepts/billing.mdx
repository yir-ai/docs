---
title: 报价与计费
description: 读取请求的估价，用 max_cost 为 Job 累计费用封顶，并了解 Job 如何计费。
---

Yir 把渠道的实际账单照实转给你。渠道实际计了费的每次尝试，按其上游费用乘以你的折扣收取，成功、失败或之后切换渠道都一样；渠道没有计费的尝试不收费，Yir 自身的交付失败与结果超时由 Yir 承担。Yir 不预留、不冻结余额。提交前可以先报价，查看估价。

## 获取报价

把准备提交的请求体发送到报价接口：

| 操作 | 接口 |
| --- | --- |
| 单个图片请求 | `POST /v1/images/quotes` |
| 单个视频请求 | `POST /v1/videos/quotes` |
| 单个音频请求（音乐、音效或语音） | `POST /v1/audio/quotes`（旧名 `/v1/music/quotes`） |
| 最多 20 个图片、视频或音乐请求 | `POST /v1/quotes` |

报价与提交使用相同的模型、输入和参数校验，但不创建 Job、不动用资金，也不锁定价格。报价请求不接受仅用于提交的 `max_cost` 和 `webhook_url`。

```json
{
  "object": "quote",
  "model": "openai/gpt-image-2",
  "currency": "USD",
  "supply": { "available": true, "issues": [] },
  "primary": { "kind": "fixed", "amount": "0.04" },
  "expected_amount": "0.04",
  "official": { "kind": "fixed", "amount": "0.053" },
  "expires_at": 1790000300
}
```

以上数值仅为示意。金额是美元十进制字符串，请使用十进制运算而非浮点数。

### 字段含义

| 字段 | 含义 |
| --- | --- |
| `primary` | Yir 首选渠道的估价，是参考价，不是收费金额或上限。 |
| `expected_amount` | 可选。Yir 对首选渠道核对余额、API Key 月度上限和 `max_cost` 时使用的估价。与 `estimate` 类价格不同，它包含参考图等已知输入费用，按用量计费的渠道还参考近期实收。它是参考价，不是上限；切到备选渠道时可能更贵。 |
| `official` | 模型原厂的参考价格，仅供对比，不代表会使用官方渠道执行。 |
| `price_difference_percent` | 可选，与 `official` 的对比，负数表示该渠道低于官方价。 |
| `supply.available` | 当前没有渠道能执行此请求时为 `false`，并带有 `issues: ["no_matching_supply"]`。 |

`max`、`single_attempt_upper_bound`、`has_verifiable_upper_bound` 和 `supply.requires_max_cost` 已弃用，仅为兼容早期客户端保留：`max` 与 `primary` 相同，其余三个始终为 `null`、`false`、`false`。不要据此做判断。

每个价格属于以下三类之一：

- `fixed`：该渠道对完整请求的标价。
- `estimate`：仅覆盖**生成输出**，用于按用量计费的模型（`estimate.output_tokens` 或 `estimate.output_megapixels` 说明估算假设）。不含输入及其他费用。
- `unavailable`：`amount` 为 `null`。未知价格绝不等于零。

`fixed` 与 `estimate` 都是对最终费用的预估；最终费用以渠道实际账单为准，可能不同。

## 设置支出上限

生成请求中的 `max_cost` 是可选项，为整个 Job 的费用封顶，例如 `"0.25"` 表示 0.25 美元，最多六位小数。没有模型要求必须提供。

- **省略时：** 每次渠道计了费的尝试按实际费用收取。
- **设置时：** Yir 只使用估价不超过 `max_cost` 剩余额度（扣除此前尝试已收费用）的渠道，切换渠道时同样适用。Job 全部尝试的累计收费不会超过 `max_cost`；实际费用更高时，差额由 Yir 承担。
- **过低时：** 没有任何可用渠道的估价在上限内时，提交以 `422 YIR_BUDGET_EXCEEDED` 拒绝，消息给出当前最低估价。失败后没有剩余尝试能满足上限时，Job 以 `YIR_BUDGET_EXCEEDED` 失败。

提交时会重新检查价格。之前获得的报价不保证相同的价格或可用性。

**警告：过紧的 `max_cost` 可能在故障切换时中断交付。** 即使 Job 已被接受，原渠道失败后也可能需要切换到更贵的渠道。如果备选渠道的估价超过扣除此前已计费尝试后的剩余预算，Yir 会跳过它；没有其他符合预算的备选渠道时，Job 将以 `YIR_BUDGET_EXCEEDED` 失败，可能无法交付结果。若业务更重视持续交付而非单个 Job 的费用封顶，可省略此可选字段；需要上限时，应为较贵的备选渠道和此前尝试的费用留出余量。省略后没有单个 Job 的费用上限，实扣可能高于报价；账户余额及其他限制仍然适用。

### 价格会变

同一请求的价格可能上涨：较便宜的渠道下线或因失败冷却、路由默认值改变了可用渠道（例如 [`routing.fidelity`](/zh/docs/concepts/routing)），或目录价格调整。设置了 `max_cost` 时，原本能通过的上限可能开始拒绝请求。

- 把 `max_cost` 当作防止费用失控的兜底，而不是锁价，在报价之上留出余量。
- 收到 `YIR_BUDGET_EXCEEDED` 时，先重新报价再决定：在新请求中调高 `max_cost`，或换更便宜的模型或规格。不要自动调高上限。
- 如果你转售生成能力并有自己的价格检查，拒单时要告警而不是静默失败，以便在用户察觉前发现价格变化。

## Job 如何计费

1. **准入**时用首选渠道的估价核对实时可用余额，不预留任何金额。之后每次尝试前，再用该渠道的估价核对一次余额。可用余额低于 5 美元且你还有其他 Job 在执行时，新 Job 停在 `queued`，每 10 秒重新核对；30 分钟后仍无法开始，则以 `YIR_INSUFFICIENT_BALANCE` 失败。
2. **渠道计了费的每次尝试**在其结束时收费：渠道上游实际费用 × 你的折扣，向上取整到 0.000001 美元。包括交付结果的尝试、切换渠道前失败的尝试，以及渠道计了费的 `YIR_CONTENT_REJECTED` 尝试（无论是拒绝提示词，还是生成了不交付的结果）。设置了 `max_cost` 时，Job 累计收费以其封顶。
3. **渠道没有计费的尝试**不收费。Yir 自身的故障也由 Yir 承担：Yir 无法交付的结果（`YIR_RESULT_DELIVERY_FAILED`），渠道始终未确认结果的尝试（`YIR_OUTCOME_TIMEOUT`），以及 Job 到达最长运行时限时仍在进行的尝试（`YIR_JOB_TIMEOUT`）。失败的尝试只按已确认的渠道账单收费，账单一直没有到达时由 Yir 承担。
4. 尝试进行中**请求停止**：该次尝试仍可能成功并收费。见[取消](/zh/docs/concepts/task-lifecycle#取消)。
5. **账单待核对。** 上游费用缺失或冲突时进入费用核对，未知费用不会按零或估价代替实际账单。

结算时余额不足以支付的，余额变为负数。余额为负时拒绝新 Job，充值补足后恢复；已准入的 Job 继续执行。Yir 不会自动扣款。

## 无法提前估价的渠道

新请求默认按渠道实际账单结算，无需选择计费模式。部分渠道即使缺少可靠的生成前估价，也可以参与普通请求；不必为计费单独指定渠道。

报价的 `supply.available` 可以为 `true`，而 `primary.amount` 为 `null`、`expected_amount` 缺省。未知价格不等于零，也不是费用上限。缺少可靠估价的路线不能接受 `max_cost`；需要费用上限时请选择有估价的渠道。

钱包必须有正的可用余额且没有未偿欠款。实扣可能高于估价；余额不足形成欠款，后续手动充值先偿还欠款，未偿清时不能提交新 Job。已有请求与 Job 保留原来的校验和计费约定。

## 读取最终费用

读取 Job 的 `billing` 了解费用。上游账单仍在核对时，结果可能已经可用，但费用尚未结清：

| 字段 | 含义 |
| --- | --- |
| `billing.status` | `pending`：费用尚未结清；`settled`：费用已结清。 |
| `billing.total_charged_by_yir` | 当前已收金额；`billing.status` 为 `settled` 时才是最终金额。 |
| `billing.compute_charges` | 算力费用明细。新 Job 有一条由 `yir` 计费的 `managed` 条目，汇总所有已收费的尝试，`status` 为 `settled`；没有任何收费时为 `waived`，金额为 `0.000`。数组可以为空。 |
| `billing.currency` | 固定为 `USD`。 |
| `billing.max_cost` | 你设置的费用上限（如有），不是收费金额。 |
| `billing.official_comparison` | 可选，与准入时冻结的本次请求完整官方价对比。 |

不再返回 `billing.savings`，请使用 `official_comparison`。渠道未计费的尝试成本，以及 Yir 关闭 Job 后才到达的渠道结果成本，均由 Yir 承担。

## 账户与 Key 的限制

- **余额。** 可用余额不足以覆盖首选渠道估价，或余额为负时，Job 以 `402 YIR_INSUFFICIENT_BALANCE` 拒绝。请在 Console 充值。可以在钱包页设置低余额邮件提醒。
- **每个 API Key 的月度支出上限。** 可选，在 [Console → API Key](/zh/docs/console#api-keys) 设置。准入时把新 Job 的估价加上该 Key 当前 UTC 自然月已结算费用；超过上限时请求以 `403 YIR_SPEND_LIMIT_EXCEEDED` 失败，不创建 Job。仍在执行的 Job 不计入，因此并发 Job 可能让 Key 略超上限。进行中的 Job 不会被中断。

## 为自己的产品定价

如果你向自己的用户转售生成能力，请把零售价格和退款规则与 Yir 的收费分开。报价的 `expected_amount`（缺省时用 `primary`）可作为定价参考，但最终费用以实际成本为准，`estimate` 类价格仅覆盖输出。需要为每个 Job 设定硬上限时，请设置 `max_cost`。等 `billing.status` 为 `settled` 后，每个 Job（包括失败的）核对一次 `total_charged_by_yir`：渠道对某次尝试计了费时，失败的 Job 也可能有费用。

结果交付不等待账单。`billing.status` 为 `pending` 时，继续查询 `GET /v1/jobs/{id}`，或处理独立的 `job.billing_settled` 通知。0 元或空 `compute_charges` 均不能证明结清；缺少状态或未知状态也不代表结清。

新请求省略 `billing_mode`。用已有幂等键重试时，保留原始请求体及旧字段；删除 `billing_mode` 会改变请求身份。无可靠估价的路线携带 `max_cost` 返回 `400 YIR_INVALID_REQUEST`；已有估价超过上限返回 `422 YIR_BUDGET_EXCEEDED`。

`gateway_fee`（目前为零且已豁免）、`supply_type`（`managed`）和 `billed_by`（`yir`）继续保留在 v1 响应中，以兼容旧客户端，新接入无需使用。`amount_basis: yir_price_rule` 是历史标识，表示实际上游费用乘以适用的渠道系数和用户折扣，不表示按报价扣费。

通过 `GET /v1/balance`（TypeScript SDK：`getBalance`，Go SDK：`GetBalance`）读取 `available_amount`、`held_amount`、`total_amount`，金额为 USD 十进制字符串。结算后可用余额与总余额可能为负。该快照不是支出授权，也不是提交 Job 的前置步骤。
